Crypto Spot Trading Platform

A high-traffic cryptocurrency exchange with a large active user base — spot buying and selling, staking, and secure wallet management, built on Laravel + Next.js and served from an Ubuntu VPS.

Laravel ExpressJS NextJS Redis Nginx PHP 8.4 MySQL

Role

Backend Developer

Stack

Laravel · Next.js

Scale

High-traffic, many active users

Overview

The platform is a full spot exchange: users deposit crypto, trade pairs against a live order book, stake assets, and withdraw back on-chain. The backend is Laravel with an ExpressJS service alongside it, and the frontend is Next.js — so effectively every piece of the product is driven by an API I built or maintained.

My focus was the server side: designing the REST APIs consumed by both the web frontend and the mobile app, keeping the trading and wallet paths correct under concurrency, and holding the system up under load with Redis, queue workers and Supervisor.

Key Features

  • Order placement & matching — market and limit orders against a live order book, with balance locks held for the life of an open order.
  • Real-time market data — tickers, order book depth and recent trades pushed to clients over WebSocket instead of being polled.
  • Wallet management — on-chain deposits and withdrawals, address generation, and confirmation tracking per network.
  • Staking — users lock assets into staking products and accrue rewards on a schedule.
  • Trading fees & tiers — maker/taker fee handling applied consistently at settlement.
  • Admin & KYC tooling — operational screens for reviewing users, approving withdrawals and monitoring activity.

What I Did

  • Designed and optimized the REST APIs powering both the Next.js frontend and the mobile app.
  • Implemented the order lifecycle — placement, partial fill, cancellation and settlement — against the user balance ledger.
  • Built the wallet layer: deposit detection, withdrawal queues and per-network confirmation rules.
  • Wrote the private-key encryption/decryption routines using Sodium, in both PHP and Node.js, so wallet keys are never stored in the clear.
  • Cached hot read paths (tickers, order book snapshots, market lists) in Redis to keep response times flat under load.
  • Moved slow work — notifications, on-chain broadcasts, settlement — onto queue workers supervised by Supervisor.
  • Deployed and tuned the app on an Ubuntu VPS behind Nginx.

Challenges & How I Solved Them

1

Balance race conditions

Two concurrent orders could spend the same balance. Order and wallet mutations run inside database transactions with row-level locking, so a balance can only be committed once — the second request fails cleanly instead of overdrawing.

2

Read load on market endpoints

Ticker and order-book endpoints were being hit constantly by every open browser tab. Serving them from Redis rather than MySQL took the pressure off the database and kept the API responsive during volatile periods.

3

Reliable deposit detection

Deposits have to be credited exactly once, even if the block scanner restarts. Deposits are keyed on transaction hash and only credited after the network's required confirmations, so a replay can't double-credit an account.

4

Protecting wallet private keys

Keys are encrypted at rest with libsodium and only decrypted in memory at the moment a withdrawal is signed — and the same scheme is implemented in both PHP and Node.js so either service can be trusted with the flow.
